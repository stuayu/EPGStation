# Codex への委譲

## 実行

```bash
codex exec --sandbox workspace-write --skip-git-repo-check \
  -c model_reasoning_effort="high" - < タスク.md > ログ.log 2>&1
```

- **プロンプトは必ずファイル経由で `-` に流す**。引数で渡すとシェルがバックティックを解釈し、
  stdin 待ちで固まることもある
- 長時間かかるので **background で実行**し、`grep -q "tokens used" ログ.log` で完了を判定する
- ログは数万行になる。`tail -n 40` で最終報告だけ読む

## タスクの書き方

**共通の制約は書かなくてよい** (`AGENTS.md` の「作業の既定ルール」に常設済み)。
タスク固有のことだけを書く。

必ず入れるもの:

1. **症状と、それを裏付ける実測値** — 「動かない」ではなく数値で
2. **すでに切り分けた範囲** — 「ここは正常と確認済み」を書くと的外れな調査を防げる
3. **完了条件** — 何が測れたら完了か
4. **報告してほしい形** — 実測値の項目を列挙する

悪い例: 「録画の再生が止まるので直して」
良い例: 「`ss=366` は 20 秒取得で 1 フレーム、`ss=1471` は 731 フレーム。位置依存。
ffmpeg のオプションは同条件で手元再現すると正常なので、パイプへ供給する側を疑っている」

## 返ってきた報告の扱い

**「修正完了」を信用しない。** 実測で確かめてから統合する。

過去に同じ症状へ「修正完了」の報告が **4 回連続で覆った**ことがある。
いずれも単体テストの通過を症状の解消と同一視していた。

確認する順:

1. **本当にリポジトリへ書かれているか** — `git status` で差分を見る。
   書込権限が無いと**別の checkout で作業して終わる**ことがある (報告には書いてある)
2. **配線されているか** — 新しい関数を作っても、実際に使われる経路から呼ばれていないことがある。
   `grep` で呼び出し元を確認する
3. **症状が消えたか** — 修正前と同じ方法で測り直す

## 事故りやすいところ

- **`config/config.yml` を書き換えられた**ことが 2 回ある。git 管理外なので `git status` に出ず、
  検証環境が静かに壊れる。触ってほしくないものはタスクにも明記する
- **同じファイル群を触るタスクを並列で走らせない**。後発が先発の変更を巻き戻す
- **前提が違ったら差し戻す**。仮説を書いて渡した場合、それが外れていても
  Codex はその線で「直した」と報告してくることがある。
  実測を添えて「その原因ではない」と伝え直す
- Codex は**メモリを持つ** (`~/.codex/memories/`)。過去の rollout 要約から、
  同種の作業で何を失敗したかを調べられる

## 委譲に向くもの / 向かないもの

| 向く | 向かない |
| --- | --- |
| 原因が特定済みの実装・修正 | 原因の切り分けそのもの (実測が要る) |
| テストの追加、期待値の更新 | 実機・実サーバでの計測 |
| ドキュメントの更新 | 本番への反映判断 |
| 定型的なリファクタリング | コミット・push・Issue 対応 |

**切り分けは指示役が実測でやり、確定した原因を Codex に渡す**のが最も速い。
