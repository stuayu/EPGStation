# Codex への委譲

## 実行

```bash
codex exec --sandbox workspace-write --skip-git-repo-check \
  -m gpt-6-luna -c model_reasoning_effort="high" - < タスク.md > ログ.log 2>&1
```

- **モデルは `-m` で明示する**。`~/.codex/config.toml` の既定は古いことがある
  (実測 2026-09-24: 既定 `gpt-5.6-luna`、指示は「GPT-6 Luna」= `gpt-6-luna`)。
  使える slug は `~/.codex/models_cache.json` を grep すれば分かる

- **プロンプトは必ずファイル経由で `-` に流す**。引数で渡すとシェルがバックティックを解釈し、
  stdin 待ちで固まることもある
- 長時間かかるので **background で実行**し、`grep -q "tokens used" ログ.log` で完了を判定する
- ログは数万行になる。`tail -n 40` で最終報告だけ読む

## タスクの書き方

**共通の制約は書かなくてよい** (`AGENTS.md` の「作業の既定ルール」に常設済み)。
タスク固有のことだけを書く。

必ず入れるもの:

1. **症状と、それを裏付ける実測値** — 「動かない」ではなく数値で
2. **すでに切り分けた範囲** — 「ここは正常と確認済み」を書くと的外れな調査を防げる
3. **完了条件** — 何が測れたら完了か
4. **報告してほしい形** — 実測値の項目を列挙する

悪い例: 「録画の再生が止まるので直して」
良い例: 「`ss=366` は 20 秒取得で 1 フレーム、`ss=1471` は 731 フレーム。位置依存。
ffmpeg のオプションは同条件で手元再現すると正常なので、パイプへ供給する側を疑っている」

## 何を渡し、何を渡さないか (実例)

**切り分けは指示役が実測でやり、確定した原因と「触ってはいけないファイル」を渡す。**

2026-09-24 に Issue 2 件を同時に片付けたときの分担:

| 作業 | 担当 | 理由 |
| --- | --- | --- |
| Issue #34 (Docker 版 Amatsukaze の設定追加) | Codex | 原因の切り分けが要らない純粋な機能追加。触るのは `src/model/amatsukaze/` + 設定定義 + ドキュメント |
| Issue #31 (音声切替の不具合) | 指示役 | 原因が未確定。ffmpeg の probe 量とパイプ入力の実測、実ブラウザでの計測が要る |

同時に走らせたので、タスクファイルに**相手が触る予定のディレクトリを名指しで禁止**した
(`client/` 配下、`src/model/service/stream/` 配下)。これを書かないと後発が先発の変更を巻き戻す。

タスクファイルには次も書いた (どれも実際に事故を防いだ):

- 設定項目を足すときの**定義元と両テンプレート、同期テストの名前** (`test/ut/config-schema-template-sync.test.js`)
- インラインの組み立て処理を**純粋関数へ切り出してから**テストで固定すること
  (`AmatsukazeEncodeTool.ts` の引数組み立て → `AmatsukazeCommandUtil.buildAddTaskCommand()`)
- 報告に「実際に組み立てられるコマンド文字列の例」を 2 通り出させる
  (既定経路と新経路。これがあると配線の確認が一瞬で済む)

## 返ってきた報告の扱い

**「修正完了」を信用しない。** 実測で確かめてから統合する。

過去に同じ症状へ「修正完了」の報告が **4 回連続で覆った**ことがある。
いずれも単体テストの通過を症状の解消と同一視していた。

確認する順:

1. **本当にリポジトリへ書かれているか** — `git status` で差分を見る。
   書込権限が無いと**別の checkout で作業して終わる**ことがある (報告には書いてある)
2. **配線されているか** — 新しい関数を作っても、実際に使われる経路から呼ばれていないことがある。
   `grep` で呼び出し元を確認する
3. **症状が消えたか** — 修正前と同じ方法で測り直す

## 事故りやすいところ

- **`config/config.yml` を書き換えられた**ことが 2 回ある。git 管理外なので `git status` に出ず、
  検証環境が静かに壊れる。触ってほしくないものはタスクにも明記する
- **同じファイル群を触るタスクを並列で走らせない**。後発が先発の変更を巻き戻す
- **前提が違ったら差し戻す**。仮説を書いて渡した場合、それが外れていても
  Codex はその線で「直した」と報告してくることがある。
  実測を添えて「その原因ではない」と伝え直す
- Codex は**メモリを持つ** (`~/.codex/memories/`)。過去の rollout 要約から、
  同種の作業で何を失敗したかを調べられる

## 委譲に向くもの / 向かないもの

| 向く | 向かない |
| --- | --- |
| 原因が特定済みの実装・修正 | 原因の切り分けそのもの (実測が要る) |
| テストの追加、期待値の更新 | 実機・実サーバでの計測 |
| ドキュメントの更新 | 本番への反映判断 |
| 定型的なリファクタリング | コミット・push・Issue 対応 |

**切り分けは指示役が実測でやり、確定した原因を Codex に渡す**のが最も速い。
