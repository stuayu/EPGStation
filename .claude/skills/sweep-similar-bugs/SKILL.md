# 同型バグの横展開

## いつやるか

**原因が「特定の書き方」だったときは必ずやる。** 1 箇所で書けた間違いは、他の場所でも書けている。

- 表示用の文字列を機械的に変換して機械可読な値に使っていた
- 2 つの定義元が同期していなかった
- ある条件分岐を片方の経路にだけ入れていた
- 単位・基準時刻・添字の取り違え

逆に、原因が「その素材固有」「その 1 行の書き間違い」なら横展開の価値は薄い。

## 手順

### 1. 間違いを「検索できる形」に言い換える

直した内容そのものではなく、**同じ間違いを生む書き方**を特定する。

| 直した内容 | 検索すべき書き方 |
| --- | --- |
| `'M2TS-LL'.toLowerCase()` が `m2tsll` にならない | 表示ラベルを `toLowerCase()` して API パスに使っている箇所 |
| 録画側だけ ID3 を map していた | 同じ cmd を組み立てている他の scope / container |
| 自動生成 cmd だけ直した | 手書き cmd・テンプレート・利用者の実設定 |

### 2. 全体を数える

```bash
grep -rn "toLowerCase()\|toUpperCase()" client/src src | grep -v "\.test\." | wc -l
```

**件数を先に出す。** 「全部見た」と言うために母数が要る。
そのうえで、検索・ソート・比較目的のものを除外して候補を絞る。

### 3. 一件ずつ「壊れているか / たまたま動いているか」を判定する

**たまたま動いているだけのものも要修正**。ラベルを変えた瞬間に壊れる。

今回の例: `HLS → hls`、`MP4 → mp4` は偶然一致するので動いていた。
`M2TS-LL → m2ts-ll` だけが壊れており、**発見が遅れた**。

### 4. 実測で確かめる

コードを読んだだけで「大丈夫」と判断しない。API なら実際に叩く。

```bash
for T in m2tsll m2ts-ll; do
  curl -s -o /dev/null -w "$T -> %{http_code}\n" "http://host/api/streams/recorded/<id>/$T?mode=0"
done
```

### 5. 再発しない形に直す

- **変換表・定数を 1 か所に置き、全経路がそこを通る**ようにする
- **型の全要素を網羅するテスト**を書く (型に要素を足したらテストが落ちる形が望ましい)
- 暗黙の変換 (`toLowerCase()` 等) をやめ、明示的な対応付けにする

### 6. 「無言で壊れる」のを直す

同型バグを生んだ場所は、たいてい**失敗が利用者に伝わらない**。
今回は 404 のまま黒画面・グルグル表示で、利用者からは原因が分からなかった。
**未知の値・想定外の応答が来たら、原因の分かる形で失敗させる**。

## 過去の実例

### 表示ラベルを `toLowerCase()` して API パスに使っていた

`M2TS-LL` を選ぶと `streamingType=m2ts-ll` へ遷移するが、API は `m2tsll` のみ受理 → 404。
**3 箇所で同じ書き方**をしていた (録画の配信選択 / 視聴履歴からの再生 / ライブ視聴)。
うち 1 ファイルには**正しい変換表が既に存在していた**のに、URL 生成では使っていなかった。

学び: **同じファイルの中に正解がある場合がある**。直す前にそのファイル全体を読む。

### 片方の経路にだけ修正を入れていた

インターレース解除の判定を新しい builder には入れたが、実際に使われる
`StreamProfileManageModel.buildCmd()` は `yadif` 直書きのままだった。
**修正が実経路に配線されているかを実測で確認する**まで「直った」と言わない。

### 定義元が 2 つあった

`config.yml.template` を更新しても、利用者の `config.yml` (git 管理外) には反映されない。
**「正」がどこにあるかを確認する。** テンプレートと実ファイル、自動生成と手書き。

## 報告の形

- **母数**: 候補を何件調べたか
- **一覧**: 各箇所と判定 (壊れている / たまたま動いている / 対象外)
- **実測**: 壊れていることを示す数値・応答コード
- **再発防止**: 何を 1 か所に寄せたか、どのテストで固定したか
